Уровень 1: Монорепозиторий и Инфраструктура (Глобальный уровень)

Проверка уязвимостей (Security Audit): Интеграция утилит вроде npm audit или Snyk для блокировки слияния, если найдена дыра в безопасности.

3. Генерация кода (Scaffolding)
   В методологии FSD создание новой «фичи» требует создания 5-6 папок (ui, model, api, index.ts). В enterprise разработчики не делают это руками.

Plop.js или Hygen (в папке tools/): Скрипты, которые позволяют написать в консоли pnpm generate feature UserAuth, и система сама создаст идеальную структуру папок с шаблонным кодом и правильными импортами.

4. Глобальная Документация (Docs & UI Catalog)
   Storybook: Изолированная среда в папке docs/storybook. Она подключает компоненты из packages/ui и позволяет дизайнерам и разработчикам тестировать кнопки и инпуты без запуска самого приложения.

ADR (Architecture Decision Records): Папка docs/adr, где в формате Markdown описывается, почему мы выбрали RTK Query, а не React Query. Это спасает при онбординге новых сотрудников.

5. Глобальное тестирование (QA)
   E2E Тесты (Playwright / Cypress): Папка e2e/, где лежат скрипты, запускающие браузер в Headless-режиме. Они логинятся в систему, кликают по кнопкам и проверяют, что supply корректно отправляет данные.

Уровень 2: Уровень отдельного проекта (apps/supply)
На этом уровне решаются задачи бизнес-логики, UX и отказоустойчивости конкретного приложения.

1. Продвинутая работа с API и Авторизация
   JWT & Refresh Token Interceptor: Логика внутри базового RTK Query (или Axios), которая перехватывает ошибку 401 Unauthorized, делает запрос за новым токеном, обновляет его в Store и автоматически повторяет упавший запрос.

RBAC (Role-Based Access Control): HOC-компоненты (Higher-Order Components) или обертки роутера, например <RequireRole role="ADMIN">. Если у пользователя нет прав, его редиректит на страницу 403.

Optimistic Updates: Настройка мутаций в RTK Query так, чтобы при добавлении расхода UI обновлялся мгновенно, не дожидаясь ответа от сервера, а при ошибке — откатывался назад.

2. Обработка ошибок (Fault Tolerance)
   Enterprise-приложение не должно показывать белый экран смерти при ошибке в компоненте.

Error Boundaries (React): Глобальный и локальные (на уровне виджетов) предохранители. Если ломается виджет графика, падает только он (появляется кнопка "Перезагрузить блок"), а остальное приложение работает.

Sentry (или аналог): Интеграция сервиса для отлова ошибок. Каждая ошибка в консоли пользователя отправляется на сервер с привязкой к версии релиза (Source Maps).

3. Валидация среды (Environment Variables)
   Zod ENV Validation: Файл конфигурации (например src/shared/config/env.ts), который проверяет process.env при старте приложения. Если DevOps забыл указать API_URL, приложение даже не сбилдится и выдаст понятную ошибку, а не упадет в рантайме.

4. Производительность и UX
   Service Workers (PWA): Настройка кэширования статики, чтобы приложение загружалось моментально даже при плохом интернете.

Скелетные загрузки (Skeleton UI): Замена стандартных "крутилок" (спиннеров) на красивые скелетоны для страниц во время работы RTK Query.

I18n (Интернационализация): Интеграция react-i18next. Даже если проект сейчас только на русском, тексты не хардкодятся в JSX, а выносятся в JSON-словари.

Как это реализовать для "Pet-проекта" (MVP Enterprise)
Вам не нужно настраивать реальный кластер Kubernetes или платить за Sentry. Чтобы показать свой уровень, достаточно сделать заглушки (mock) или базовые реализации.

Примеры для реализации в вашем проекте:

Создать .github/workflows/ci.yml — написать пайплайн, который прогоняет lint и tsc при пуше. Это бесплатно и круто выглядит в репозитории.

Написать один скрипт генерации (Plop.js) — проверяющий будет в восторге, увидев автоматизацию создания FSD-слайсов.

Сделать ErrorBoundary и Zod-валидацию ENV — это пишется за 30 минут, но показывает колоссальную заботу об отказоустойчивости.

Создать Storybook для 2-3 компонентов из packages/ui.

Настроить RBAC обертку для React Router (даже с фейковой авторизацией).

1. Дыры в сборщике (Webpack & Производительность)

Анализ размера бандла: В pet-проектах всем плевать на размер JS-файла. В enterprise за каждый лишний килобайт идет борьба.

Что добавить: Плагин webpack-bundle-analyzer (запускается по флагу pnpm build --analyze).

2. Дыры в сетевом слое и API (RTK Query)
   Мы создали baseApi, но он слишком "наивный".

Mock Service Worker (MSW): В enterprise фронтенд не ждет, пока бэкенд напишет API.

Что добавить: Интеграцию MSW. На уровне браузера перехватываются запросы от RTK Query и возвращаются фейковые данные (JSON-моки). Это позволяет разрабатывать фичи полностью автономно.

Сложный Interceptor для токенов (Refresh Token Flow): Текущий fetchBaseQuery не умеет обрабатывать протухшие токены.

Что добавить: Кастомную обертку над fetchBaseQuery (mutex), которая при ошибке 401 ставит все запросы на паузу, обновляет токен через /refresh эндпоинт и повторяет упавшие запросы.

Строгая валидация контрактов (Zod/Yup): RTK Query верит бэкенду на слово (через as ExpensePlan). Если бэкенд пришлет string вместо number, TypeScript этого не поймает (он работает только в процессе сборки), и приложение упадет в рантайме.

Что добавить: Валидацию DTO (Data Transfer Object) на лету с помощью Zod внутри хуков RTK Query (transformResponse).

3. Дыры в безопасности и качестве кода (Линтеры и Тесты)
   Мы настроили базу, но не "закрутили гайки".

Доступность (Accessibility / a11y): Корпоративный софт обязан соответствовать стандартам (WCAG).

Что добавить: Плагин eslint-plugin-jsx-a11y в packages/config-eslint, который будет ругаться, если у <button> нет aria-label или у <img> нет alt.

Проверка переменных окружения: Если DevOps забудет добавить REACT_APP_API_URL в .env, приложение тихо сбилдится с ошибками.

Что добавить: Скрипт env.ts с Zod-схемой, который валидирует наличие и тип всех переменных окружения в момент старта Webpack.

Отсутствие E2E-тестов и Visual Regression:

Что добавить: Cypress или Playwright (папка e2e/ в корне). Также инструмент Chromatic или Loki для проверки, не "поехали" ли пиксели в кнопках из packages/ui.

4. Дыры в управлении монорепозиторием
   Наш pnpm и turborepo настроены локально, но не готовы к CI/CD и командной работе.

Кэширование Turborepo на основе .env: Если поменяется .env файл, Turborepo достанет старую сборку из кэша (он не знает, что .env влияет на билд).

Что добавить: Блок globalEnv и globalDependencies в turbo.json.

Управление релизами и Changelog: Как узнать, в каком приложении что изменилось?

Что добавить: Пакет @changesets/cli. При каждом PR разработчик запускает pnpm changeset и описывает изменения. CI/CD сам повышает версии в package.json и пишет CHANGELOG.md.

Автоматизация обновлений зависимостей:

Что добавить: renovate.json или Dependabot, чтобы бот сам создавал PR на обновление React, Webpack и других библиотек.

Пайплайн CI/CD:

Что добавить: Файл .github/workflows/main.yml, который при пуше делает: установку зависимостей -> проверку типов -> линтер -> тесты -> сборку (с использованием кэша Turborepo).

5. Дыры в архитектуре приложения (React & FSD)
   Внутри apps/supply мы настроили папки, но забыли про "броню" самого React.

Error Boundaries: Сейчас любая неперехваченная JS-ошибка убьет всё приложение (белый экран).

Что добавить: Компонент ErrorBoundary из react-error-boundary на уровне app (глобальный) и на уровне каждого widget (локальный).

Интернационализация (i18n): В коде (в index.tsx и страницах) мы захардкодили русский текст.

Что добавить: Пакет i18next и react-i18next, вынести все тексты в JSON-словари.

Дизайн-система (Storybook): Мы создали packages/ui и packages/config-tailwind, но разработчики finance не знают, какие кнопки там есть, пока не залезут в код.

Что добавить: Развернуть Storybook, чтобы компоненты UI-кита можно было смотреть в браузере с интерактивными пропсами.

1. Качество кода и автоматизация (Quality Assurance)
   В логах сборки я видел, что у тебя есть пакеты config-eslint, config-typescript и установлен husky. Это хорошо, но для Enterprise этого мало.

Тестирование (Unit/Integration): В turbo.json должна быть задача test. Для монорепозитория на Vite/Vite-based инструментах идеально подходит Vitest.

E2E Тестирование: Для критических путей (например, оформление поставки в supply или проводка в finance) необходим Playwright. В Enterprise без автотестов бизнес-логики деплой превращается в игру «повезет — не повезет».

Enforcement (Принуждение): Настрой GitHub Branch Protection. Ветку master нужно закрыть для прямых пушей. Слияние (merge) разрешать только если:

Пройдены все тесты в CI.

ESLint/Prettier не выдали ошибок.

Есть как минимум один апрув от коллеги.

2. Наблюдаемость (Observability)
   Сейчас твои приложения работают как «черные ящики». Если упадет конкретный запрос в finance, ты узнаешь об этом только от пользователя.

Error Tracking (Sentry/GlitchTip): Интегрируй Sentry. Это позволит видеть ошибки фронтенда и бэкенда в реальном времени с полным трассировочным стеком (stack trace) и данными о пользователе.

Централизованные логи (Loki + Grafana): Поскольку у тебя несколько приложений, читать логи через docker logs — это мучение. Настрой стек Loki-Promtail-Grafana, чтобы искать логи по всем сервисам в одном окне.

Метрики (Prometheus): Тебе нужно знать потребление RAM/CPU контейнерами и время ответа (latency) API, чтобы вовремя масштабировать VPS.

3. Безопасность (DevSecOps)
   Твой текущий подход с секретами в GitHub — верный, но безопасность Enterprise шире.

Сканирование зависимостей: Включи GitHub Dependabot или интегрируй Snyk. Они будут автоматически создавать PR, если в твоем package.json найдена библиотека с известной уязвимостью.

SAST (Static Analysis): Добавь в CI шаг с SonarQube или CodeQL. Это поиск «плохого запаха» в коде: потенциальных дыр, утечек памяти или захардкоженных секретов, которые ты случайно пропустил.

Контейнерная безопасность: Используй Trivy в CI для сканирования твоих Docker-образов на наличие уязвимостей в системных библиотеках (alpine/nginx).

4. Архитектура и Работа с данными
   Миграции БД: Если у тебя появится общая база, управление схемой данных должно быть автоматизировано. Используй Prisma или Drizzle ORM. Миграции должны запускаться как отдельный этап (Stage) в CI/CD перед деплоем приложений.

API Documentation (Swagger/OpenAPI): В Enterprise бэкенд и фронтенд часто пишут разные люди (или даже разные команды). Наличие Swagger-документации, которая генерируется из кода бэкенда — стандарт.

Версионирование API: Сразу заложи в пути API версию (например, /api/v1/finance). Это позволит обновлять бэкенд, не ломая фронтенд у пользователей, которые еще не обновили вкладку в браузере.

5. Developer Experience (DX)
   Документация: В корне репозитория должен быть CONTRIBUTING.md и подробный README.md. Новый разработчик должен уметь запустить проект одной командой (например, pnpm dev) и понимать структуру папок.

Conventional Commits: Ты уже используешь commitlint, и это супер. Это позволяет автоматически генерировать CHANGELOG.md, чтобы бизнес понимал, какие фичи уехали в релиз.

Генераторы (Plop/Turborepo Generators): Создание нового приложения или пакета должно быть автоматизировано. Разработчик пишет turbo gen app, вводит название, и Turbo создает папку с правильным конфигом, Dockerfile и Nginx.
